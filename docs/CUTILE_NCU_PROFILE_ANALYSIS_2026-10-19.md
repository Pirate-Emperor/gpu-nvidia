The “estimated local speedup” numbers are Nsight Compute rule heuristics, **not measured optimization wins or guarantees**. The optional `smsp__pcsamp_sample_count` metric was unavailable, so Nsight did not provide its more detailed warp-stall sampling locations. Treat the rule output as a directional diagnosis rather than precise attribution of every stall.

## Interpretation and decision

1. **The clearest resource constraint is shared memory.** Nsight's basic Occupancy section identifies shared memory as the block-level limiter: one CTA per SM and only about 8.3% theoretical/achieved occupancy. Static per-block shared memory rises from about 65.5 KiB for 64×64 to about 81.9 KiB for 64×128. Register use is also high at 231–255 registers/thread.
2. **Neither case is near peak overall compute or DRAM throughput.** The medium workload reaches 18.8% SM compute / 22.9% DRAM throughput; the longer batched workload reaches 30.3% compute / 11.9% DRAM. Low scheduler eligibility and the execution-pipeline-stall rule suggest the kernel often cannot issue instructions every cycle with its present active-warps/resource footprint.
3. **Do not change the default solely based on these reports.** Keep 64×64 as the general default and 64×128 as a promising specialization for the longer batched workload based on the already-measured benchmark. A follow-up optimization experiment should target shared-memory/register pressure or instruction scheduling, create a new kernel version, rerun correctness first, then repeat controlled performance measurements before adopting it.
4. **No counter-permission workaround was required.** The current RTX 4060/driver setup profiled successfully. The historical A100 `ERR_NVGPUCTRPERM` is unrelated to these reports.
